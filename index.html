M▼ MarkdownDrift

There is no "Markdown". There are four renderers you actually ship to - CommonMark, GitHub's GFM, Python-Markdown, and the 2004 original - and they disagree on lists, headings, tables, links and emphasis. Your README renders one way on GitHub and another in your Sphinx docs. MarkdownDrift reads your file and names every line that will drift, with the rule that causes it.

Divergences it catches

Your numbered list renumbers itself. 5. five keeps its number in CommonMark (<ol start="5">). Python-Markdown and markdown.pl silently restart at 1.
#hashtag vs # heading. #foo is a heading in Python-Markdown and the 2004 original. CommonMark requires the space - it's a paragraph. Your issue references turn into headings.
The list that isn't one. 1) first is a legal ordered-list marker in CommonMark and GFM. Python-Markdown gives you a plain paragraph.
Fenced code collapses. Triple backticks are a code block in CommonMark and GFM. Python-Markdown core has no fences - they melt into an inline code span.
Your nested list flattens. Two-space indentation nests under CommonMark's marker-width rule. Python-Markdown wants four spaces - your children become siblings.
Links, tables, checkboxes, strike. Bare URLs, pipe tables, - [ ] and ~~strike~~ exist only in GFM-land. Everywhere else they are literal text.

How it's verified

The Python-Markdown column is not somebody's documentation: the repo's test suite runs the real python-markdown 3.10.3 on every corpus case and fails the build if a label drifts from the library's actual HTML output. CommonMark labels cite CommonMark 0.31.2 sections; GFM covers its published extensions; markdown.pl is the historical reference. The engine itself is a detector, not a renderer - it flags constructs, it does not pretend to reimplement four parsers.
